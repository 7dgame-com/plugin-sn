# SN 分发管理功能说明

本独立仓库只包含 SN 管理前端插件及相关文档。网页管理、SN 生成和数据库迁移由
`xrugc-platform` 的主 API 提供；Unity/Rokid 的 SN 激活、登录、刷新和退出由
`backend/yii3-a1`（y1）原生提供，复用其现有用户名密码登录的 HS256 Token 体系。
本仓库不包含后端或 Unity/Rokid 客户端实现。

SN 分发管理用于给 Rokid 客户端分配账号登录凭证。获得插件访问权限的账号为已有普通账号生成 SN，设备首次提交自己的 UUID 和 SN 完成绑定；以后用相同凭据登录该账号，无需输入用户名和密码。初始只有 root 可管理，root 可通过插件配置调整访问范围。

本说明面向管理员、产品和运维。**2026-09-29 的 y1 认证迁移仅在本地实现，尚未部署开发或生产。** 本次版本中主 API 的 `sn-activate/sn-login` 返回 `410 Gone`，Unity 须切换到已核验的同环境 y1 入口。

2026-09-28 已完成的是主 API + identity 历史版本验收：当时支持 16 位新码和 32 位历史码，管理权限可动态调整，开发、生产最终均为 `admin-only`（admin + root）。历史版本和验收边界记录在平台仓库的 `docs/sn-management/DEVELOPMENT_DEPLOYMENT_20260927.md`，不能证明本次 y1 接口、16 位限定或账号删除作废改动已上线。

Unity/Rokid 客户端尚需按 [Rokid 设计指南与 Unity 开发交接](UNITY_CLIENT_README.md) 实现；真实设备 UUID、启动、休眠唤醒和到期自动重登未因此完成验收，也未等待 Access Token 自然存活满 3 小时。此前发布验收 SN 已停用留档，客户端联调需要新的专用测试码。

新增的“删除账号后 SN 永久作废”规则已在本地实现，尚未部署，需配套后端增量迁移；此前发布记录不包含本项。

## 账号、SN 与设备的关系

| 对象 | 规则 |
| --- | --- |
| 管理者 | 正常启用、符合当前插件 `access_scope` 的普通登录会话；默认 root-only，可由 root 调为 admin-only 等。SN 设备会话始终无管理权限。 |
| 绑定账号 | 必须是已有、正常启用的普通账号：`status=10`，且没有 `root`、`admin`、`manager` 角色。 |
| 一个 SN | 生成时固定一个账号，首次激活时固定一个设备 UUID，之后不能修改。 |
| 一个账号 | 可以关联多个 SN；给每台设备各分配一个 SN，即可让多台设备登录同一个账号。 |
| 一个设备 UUID | 在 SN 系统内只能占用一个 SN；该 SN 停用或作废后也不会释放 UUID。 |
| SN 格式 | 16 位 Crockford Base32，按每 4 位分组显示为 19 个字符；y1 和 Unity 仅接受 16 位。历史 32 位码可管理留档，但不能在新设备接口登录，不截断或补齐。 |
| SN 有效期 | 当前为永久码，没有到期时间、续期或期限配置；实际使用仍受 SN 开关和账号状态限制。 |

SN 和设备绑定业务只使用既有的一张 `device_sn` 授权表，记录所属账号、SN 凭证、`device_uuid`、启用状态及相关时间。生成时 `device_uuid` 为空，y1 首次激活时写入并保持唯一。主 API 与 y1 共享同一权威库，迁移认证入口不增加表、不复制绑定；用户、审计和 y1 登录会话继续复用现有系统。

旧 `device` 表继续保留，本功能不读写它。旧设备记录或其 `owner_id` 不参与 SN 激活冲突判断，UUID 是否冲突只以 `device_sn` 中的绑定为准。

## 管理员可以做什么

root 在系统管理的插件注册页面编辑 `sn-management` 的访问范围：`root-only` 允许 root；`admin-only` 允许 admin 和 root；`manager-only` 再允许 manager；`auth-only` 再允许 user。把范围从 `root-only` 改为 `admin-only` 即授权 admin 管理整个 SN 插件，改回即可收回，不需要修改代码或重新构建插件。

注册示例默认 root-only；本轮开发、生产实际已保存并核实 admin-only，即 admin 和 root 均可管理，之后可随时改回。实际权限以当前环境配置为准。

主后端逐请求检查当前配置。权限收回后，已打开的 admin 页面在下一次管理请求收到 403 时清除会话并关闭敏感界面，不自动重试；重新授权后可手动验证。主站菜单可能需刷新后才更新。调整管理权限不会允许管理员账号绑定 SN，也不会给设备 SN 会话增加管理权限。

如果运行中无法读取权限配置，前端收到配置服务的专用 503 错误后也会清除会话、关闭敏感界面并忽略迟到响应，提示稍后重试。普通业务暂时失败不会被当作权限撤销。

| 功能 | 当前行为 |
| --- | --- |
| 生成 SN | 搜索并选择一个可绑定的普通账号，每批生成 1–100 个，可填写最多 500 字的备注。 |
| 分发凭证 | 生成成功后查看、复制本批完整码，或下载 CSV；之后也可从列表重新查看完整码。 |
| 查看列表 | 按账号、SN 尾号或 UUID 搜索，按状态或账号筛选，支持分页。 |
| 查看设备状态 | 列表展示 SN 尾号、账号、状态、UUID、生成时间、激活时间、最近登录时间和备注。 |
| 查看详情 | 查看账号和设备绑定信息、相关时间，以及最近 100 条操作审计。 |
| 导出 | 导出所选 SN 或本批次 SN 为 CSV，每次最多 100 条；导出包含完整 SN，需按登录凭证保管。 |
| 停用与恢复 | 停用单个 SN，或恢复其原有授权；已永久作废的 SN 不可恢复。 |
| 编辑备注 | 修改备注，便于登记设备用途、分发批次等信息。 |

生成、首次激活、查看完整码、导出、停用、恢复和备注更新会记录操作审计。普通列表和详情只显示 SN 尾号；完整 SN 不写入审计日志。最近登录时间记录成功的 SN 激活登录或重登，不代表设备当前在线，也不是完整登录历史。

如果生成请求因网络中断而未确认成功，先刷新列表核对结果，再决定是否重新生成，避免重复发行。CSV 导出已做公式注入防护；完整码仍应只分发给目标设备使用者。

## 从分发到登录

1. 获得当前配置授权的账号进入主系统的 **SN 分发管理** 插件，选择普通账号并生成所需数量的 SN。
2. 管理员把不同 SN 分发给不同 Rokid 设备。一台设备保留一个 SN；需要共用账号的设备使用绑定同一账号的不同 SN。
3. Rokid 首次向同环境 y1 的 `POST /v1/auth/sn-activate` 提交 16 位 SN 和稳定设备 UUID。y1 完成绑定后签发与其原用户名密码登录一致的 HS256 Token。
4. 设备以后启动或 Access Token 到期时，以相同 SN 和 UUID 调用 y1 的 `POST /v1/auth/sn-login`，继续登录同一账号。后续 y1 业务请求使用原有 Bearer Token 和账号权限。
5. 需要暂停某台设备的授权时，管理员停用对应 SN；确认恢复使用后，可恢复同一个 SN。

以上设备接口路径属于 y1。管理插件仍通过主站/插件 `/api` 代理连接主 API，Unity 单独使用部署环境提供的 y1 根地址。主 API 的 `sn-activate/sn-login` 在本次版本返回 410，不代理或重定向凭据，也不作为备用入口。详细协议见 [主 API 管理与 y1 认证说明](BACKEND_API_README.md) 与 [Unity 客户端实现说明](UNITY_CLIENT_README.md)。

y1 的 `/v1/auth/refresh` 与 `/v2/auth/refresh-token` 均可轮换设备 Refresh Token 并保留 SN 来源；Rokid 默认仍采用 SN + UUID 自动续登录。`/v1/auth/logout` 撤销指定 y1 刷新会话，不解除绑定。主 API/identity 旧会话不能直接交给 y1，切换时须使用原 SN + UUID 重新登录。

同一 SN 和同一 UUID 重复激活是幂等操作。激活绑定已经提交但响应丢失时，设备可以用原凭据重试。把已激活 SN 输入另一台设备，或用另一个 SN 占用同一 UUID，都会发生绑定冲突，不会自动换绑。

## 状态与使用边界

| 状态 | 含义及后续操作 |
| --- | --- |
| 未激活 | SN 已生成且启用，尚未绑定 UUID；需要先完成首次激活。 |
| 已激活 | SN 已启用且完成绑定，原设备可以登录所属账号。 |
| 已停用 | 当前禁止新登录和刷新；可能是未激活前停用，也可能是激活后停用。恢复后回到原来的未激活或已激活状态。 |
| 已作废 | 绑定用户账号已删除；全部所属 SN 永久失效。保留原账号 ID、UUID 和已有操作记录，没有恢复入口。 |

停用提交后开始的新登录和 Token 刷新会被拒绝。已通过授权检查的在途请求可能完成，已经发出的 Access Token 可以继续使用到自身过期，剩余时间最长为 3 小时。因此，停用不保证设备立即离线。停用单个 SN 不会同时停用账号下的其他 SN，也不会关闭该账号的密码登录。

停用不会清除 UUID。恢复已激活 SN 只恢复原设备的使用资格，不能用于转交另一台设备。账号暂时停用或获得 `root/admin/manager` 角色后，会失去 SN 登录资格，但不会因此永久作废。

删除绑定用户账号会立即将该账号的全部 SN 永久作废，包括未激活、已激活和已停用的 SN；后续 y1 激活、登录、刷新和 Access 鉴权均拒绝，主 API 的历史 SN 会话同样检查作废状态。删除回滚则不会作废。重新创建同名或同 ID 账号也无法恢复原码，UUID 仍被保留。列表可按“已作废”筛选，详情显示“账号已删除”和原账号 ID；允许查看、导出与修改备注用于留档，不能停用或恢复。已有审计保留，不伪造历史删除时间。

当前不提供解绑、换机、重新绑定账号、直接删除 SN、设置有效期或续期功能。设备重装或更换后，如果客户端报告的 UUID 改变，现有 SN 不会自动接受这个新 UUID。

UUID 是客户端声明的设备标识，不是硬件真实性或防克隆证明。客户端必须使用稳定的设备标识，不能每次启动随机生成；服务端会去除首尾空白并转成小写。SN 属于长期登录凭证，不应放入公开链接、日志、遥测或截图。SN 登录会话也不允许生成二维码登录码、OIDC 换票，或修改账号密码、邮箱。

## 本地使用与生产部署

本地使用 Node.js 24.x 和 pnpm 9.15.0。在本插件仓库根目录执行：

```sh
corepack pnpm install --frozen-lockfile
corepack pnpm dev
```

若插件位于平台仓库的 `xrugc-platform/plugins/sn-management`，也可以从
`xrugc-platform` 根目录执行 `./start-dev.sh --sn-management`；该启动脚本由平台仓库提供。

插件默认端口为 `3018`，通过主系统 `/plugins/sn-management` 进入；直接打开插件端口只会显示从主系统进入的提示。后端及其依赖需另行准备。主站登录、插件代理和 SN 管理 API 必须连接同环境主 API，Unity 连接同环境 y1；不要将插件上游改为 y1。更多本地配置见 [插件 README](../README.md)。

账号删除永久作废的升级另需执行 `m260928_150000_preserve_revoked_device_sn`。迁移及升级全部主 API 与 y1 节点期间暂停账号删除与 SN 生成；先迁移、再升级后端和插件。旧版本已经级联删除的 SN 记录无法补回。

生产开放顺序如下：

1. 准备兼容主 API，按目标环境状态执行 `device_sn` 及相关迁移，保留 SN 加密 keyring 和可信插件配置读取，依据 [主 API 管理与部署说明](BACKEND_API_README.md) 操作。迁至 y1 无需新表或回填历史 SN，旧 32 位码不能截断使用。动态管理权限继续由 system-admin 可信配置接口和主 API `/v1/plugin-sn/access` 配合实现，不能仅通过前端登记授权。
2. 更新 y1 设备认证服务，连接同一权威 MySQL；各 y1 节点共享同环境 Redis 逻辑库、限流状态和现有 HS256 `JWT_KEY`。y1 不调用 identity，不需要主 API 的 AES keyring。主 API/identity 的原有网页与历史 SN 会话兼容配置保持，不删除已有来源字段；两套 Token 不混用。详情见平台仓库 `xrugc-platform/backend/yii3-a1/docs/device-sn.md`。
3. 构建并部署插件，配置指向主 API 的单一 `APP_API_1_URL`；Unity 切换到已核验的 y1 入口。插件拒绝配置第二上游。多节点须先验证共享权威库及各自签名、会话状态的一致性；主 API 与 y1 使用不同签名体系，不应配置成同一 Token 入口。
4. 在系统管理插件中按 [注册配置示例](../plugins.json.example) 登记 `sn-management`，填写实际插件业务 URL，初始使用 `accessScope: root-only`，之后可按需修改。本地 `developmentOnly` 登记不会自动进入生产；业务 URL 不应填写 Portainer 管理地址，入口说明见平台仓库 `xrugc-platform/docs/deployment-topology.md`。
5. 在对应开发环境验证 root 默认可用、admin 默认拒绝、配置改为 admin-only 后可分发、改回后已打开页面拒绝继续操作，以及 SN 设备会话始终无管理权限；再验证主 API 管理生成→y1 激活、重登、两种刷新、退出、停用与恢复，以及主 API 旧认证入口返回 410。记录各服务环境和实际版本后按平台 CI 流程推进。平台仓库 `xrugc-platform/docs/sn-device-login-verification.md` 仅为历史实现检查，不能代替本次部署验收。

本说明不表示已经完成生产部署、线上数据库迁移或 Unity 客户端发布。新增和维护密钥时应使用部署 secret，并按后端说明保留旧解密密钥；数据库与密钥应配套备份。
